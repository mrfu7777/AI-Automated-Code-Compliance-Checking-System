# M1 Walking Skeleton

- Version: 0.2.0
- Status: Complete
- Date: 2026-09-09

## Outcome

M1 delivers the first real vertical workflow on the M0 architecture: create a project, upload an
immutable PDF version, store the original object, create a persistent asynchronous job, process
it in Celery, and display file versions and job state in React.

## Delivered

- Tenant-scoped project create, list, and detail APIs
- Deterministic local development actor with an explicit non-production security boundary
- Streaming PDF validation, SHA-256 calculation, and a configurable 150 MB limit
- MinIO original-object storage and short-lived browser download URLs
- Append-only versions for each logical project file
- Persistent file metadata in PostgreSQL
- Celery metadata processor with queued, running, succeeded, and failed states
- Manual failed-job retry with a stored attempt limit
- Project file, version, and job list APIs
- Request ID propagation into jobs and audit events
- Project creation, upload, download, retry, success, and failure audit records
- React project, upload, version, progress, failure, and retry workspace
- Additive Alembic migration from the M0 schema
- Backend integration tests with fake storage and dispatch boundaries
- Frontend component tests and production build validation

## Stable contracts for M2

M2 must extend rather than replace:

- ProjectFile and immutable FileVersion records
- MinIO object keys and SHA-256 metadata
- the ObjectStorage boundary
- the persistent Job state machine and retry endpoint
- request-linked AuditEvent records
- project-scoped file and job APIs
- the React progress and error states

Regulation ingestion becomes a new file purpose and worker processor. It must not introduce a
second upload service, a second job table, or mutable source files.

## Known limitations

- M1 accepts PDF only and verifies its header, not its full internal structure.
- The local actor is not production authentication.
- The example worker verifies object metadata; it does not extract text or run OCR.
- Object storage and PostgreSQL do not share an atomic transaction. Upload cleanup is best-effort,
  and production operation will require orphan reconciliation.
- Job progress is polled; push updates are not implemented.

## Verification

- Ruff passes.
- Strict mypy passes.
- Twelve backend tests pass and coverage remains above the 80 percent gate.
- Frontend ESLint, two component tests, TypeScript compilation, and production build pass.
- Alembic exposes one head and the new migration is additive from M0.
- Docker Compose defines PostgreSQL, Redis, MinIO, API, worker, and web services.
