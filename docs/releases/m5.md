# M5 Drawing Evidence Workbench

- Version: 0.6.0
- Status: Complete
- Date: 2026-09-15

## Outcome

M5 adds a practical PDF drawing pipeline and an architect-facing evidence workbench without
replacing the M1-M4 contracts. Drawing pages become previewable evidence, positioned labels become
reviewable fact candidates, calibrated paths become derived measurements, and every check finding
can be reviewed beside its project evidence and regulation basis.

## Delivered

- PDF drawing page rendering with text-layer extraction and local OCR fallback
- Drawing title, number, floor, scale, dimension, room, door, stair, and exit candidates
- Page number, bounding box, page size, method, confidence, excerpt, and extractor version evidence
- A shared candidate persistence service used by both M4 documents and M5 drawings
- Drawing page preview URLs backed by the existing immutable object store
- Architect-created object, dimension, scale, and calibrated path annotations
- Deterministic polyline length calculation using a pixels-per-metre calibration
- Existing candidate/conflict/verify/reject workflow for all drawing-derived facts
- A three-column React workbench for findings, project evidence, and regulation evidence
- Finding workflow state, assignee, notes, audit events, and an additive Alembic migration
- Evidence-consistent JSON, PDF, and XLSX exports
- Twenty-five review-required rule authoring templates
- A drawing Golden Set and end-to-end tests for extraction, persistence, preview, measurement,
  confirmation, workbench navigation, workflow updates, and reports

## Continuity audit

M5 deliberately introduces no drawing-fact table and no second review workflow. The source PDF is
still an M1 `FileVersion`; processing is still an M1 `Job`; PDF rendering and OCR still use the M2
extractor; drawing candidates are still M4/M3 `ProjectFact` and `Evidence` records; confirmation is
still performed by the M4 candidate endpoints; and compliance still runs against the M3 immutable
snapshot and deterministic engine. The new `fact_candidates` service removes duplicated conflict
logic so document and drawing pipelines cannot silently diverge.

The only database change adds review-management fields to `CheckResult`. It is additive and keeps
all historical results valid with an `open` default.

## Safety boundaries

- OCR and label recognition create candidates, never compliance conclusions.
- Low-confidence and conflicting candidates cannot enter a check until an architect verifies them.
- Counts are visible-label inventory signals, not proof that the drawing is complete.
- Path length is deterministic but depends on the architect-supplied calibration and points.
- The initial drawing pipeline supports PDF input; native DWG/DXF geometry is deferred.
- The twenty-five templates are authoring aids, not approved interpretations of Chinese fire code.
- Reports are preliminary decision-support outputs and do not replace statutory review.

## Verification

- Ruff, strict mypy, Alembic head validation, and backend tests pass.
- Backend coverage remains at or above the enforced 80 percent threshold.
- Frontend lint, Vitest, TypeScript compilation, and production build pass on Node.js 24.
- OpenAPI documentation contains the M5 drawing, annotation, workbench, finding, and report routes.
- A public Ellis Island HABS drawing sheet completed the real OCR path with 63 positioned text
  lines and 17 conservative candidates; this validation also exposed and fixed NumPy-array handling
  in the shared RapidOCR adapter used by both M2 and M5.

## Next milestone

M6 can compare file versions, invalidate facts whose drawing evidence changed, and schedule
incremental rechecks. It must reuse `FileVersion`, `ProjectFact.supersedes_id`, published rule-pack
snapshots, `CheckResult`, and the M5 workbench rather than adding a second revision or review model.
