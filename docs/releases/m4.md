# M4 Project Fact Extraction

- Version: 0.5.0
- Status: Complete
- Date: 2026-09-13

## Outcome

M4 converts project PDF, DOCX, XLSX, and IFC files into reviewable fact candidates. Every candidate
retains its immutable file version, precise source location, excerpt, confidence, and extractor
version. Conflicting sources remain explicit, and only an architect-verified candidate can enter
the existing M3 deterministic compliance workflow.

## Delivered

- One upload path for PDF, DOCX, XLSX, and IFC with extension, media-type, signature, size, and
  SHA-256 validation
- Automatic project-document classification by supported file type
- Reuse of M2 PDF text-layer extraction and local OCR fallback
- DOCX paragraph and table-row extraction with stable paragraph or table locations
- XLSX value extraction with worksheet and cell-range locations
- IFC parsing through IfcOpenShell, including storey, space, door, and stair counts plus property-set
  scanning
- A versioned deterministic extractor catalog with fifteen common fire-review fact types
- Typed numeric, integer, text, and boolean candidates with units and confidence
- Persistent `project.extract` tasks in the existing Celery job lifecycle
- Candidate and evidence APIs scoped to the actor's organization
- Explicit conflict marking when sources disagree on the same fact and scope
- Architect verify and reject decisions with reasons and audit events
- Supersession of older verified values without overwriting machine output or evidence
- React candidate review workflow with evidence, confidence, conflict state, and decisions
- A committed Golden Set plus PDF, DOCX, XLSX, IFC, conflict, decision, and M3-bridge tests

## Continuity audit

M4 does not introduce a parallel extraction database. Uploaded documents remain M1
`ProjectFile`/`FileVersion` records, extraction remains an M1 `Job`, PDF processing calls the M2
PDFium/OCR service, and output is stored in the M3 `ProjectFact`/`Evidence` contract. The M3 snapshot
builder already selects current verified facts, so verifying an M4 candidate makes it immediately
eligible for the same deterministic rules. Candidate and conflicting records are filtered out.

The milestone required no database migration because the M0 schema and M3 additive migration had
already reserved candidate status, confidence, extractor version, verifier identity, supersession,
and evidence links. This is intentional proof that the staged design remains cumulative.

## Supported fact catalog

The versioned `m4.project-extraction.v1` catalog recognizes building height, above-ground floor
count, building use, fire-resistance rating, fire-compartment area, safety-exit count, clear widths
for egress doors, corridors, and stairs, evacuation travel distance, and whether fire elevators,
automatic sprinklers, smoke control, fire alarm, and fire hydrants are provided. Patterns support
the initial Chinese and English labels needed by the pilot.

## Safety boundaries

- Extraction is structured assistance, not a compliance decision.
- A candidate never enters a check before explicit verification.
- Conflicts never choose a winner automatically.
- Evidence and the original machine value remain immutable after a decision.
- The initial patterns do not interpret complex floor-plan geometry or infer hidden design intent.
- IFC counts are model inventory signals; an architect must decide whether the model is complete.
- Outputs remain preliminary and do not replace statutory review or professional judgment.
